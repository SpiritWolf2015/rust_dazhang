## Goals / Non-Goals

**Goals:**

- G1 按用户拍板改 `w3-core` 真复活：英雄阵亡后经本族祭坛排队复活，**恢复同一个英雄实体**（同一 `EntityId`、等级 / 经验 / 技能等级 / 6 格背包保留），英雄死亡不判负（R6.3 / R11.2）。
- G2 新增死亡登记 / 复活队列 / 费用三组权威状态，全部同步进 FNV-1a 状态哈希、由 `SNAPSHOT_VERSION`（按 Q1 拍板 bump 4）定义的快照与 `first_difference()`，跑通 determinism 26 项 + 「改坏验红」，golden hash 基线按新实现如实更新（ADR 0002 / `CODEBUDDY.md §5`）。
- G3 费用 / 时间读冻结合成原创编译期整数常量 `[待核]`、随等级表驱动计算、祭坛与酒馆参数分离；费用提交事务与效果执行链分离，取消 / 失败事务性退款 + 恢复死亡登记（R6.3 / 主 `gameplay-systems/spec.md:19`）。
- G4 死亡登记用整数帧号 `death_frame: u64` + `BTreeMap` 确定性有序容器 + 定义层类别 `CATEGORY_ALTAR` 驱动，**不用**墙钟 / 全局静态字典 / `HashMap` 迭代顺序 / 建筑名白名单（ADR 0002 §2-3 / R1.2 / R13.3）。
- G5 四件套一次成文同步修订主 specs 口径（不改主 specs 正文、用 MODIFIED delta 表达）、表现层 HUD 队列只读派生、与 P8.2 `orc-faction/spec.md:39` 边界衔接、参考项目对照结论与锚完整落盘。

**Non-Goals:**

- 「只读派生降级 / HUD 假复活」（P1 被否 B）、「先做 P8.5e 迷雾」（被否 C）、复活 `spawn` 新实体、墙钟死亡登记、写死经典数值 / 冒充原版。
- 酒馆买活（R6.3 后半 / R9）、多英雄复活队列 UI、复活后技能点 / 装备态一致性回归（按 Q4 拍板全部按推荐留后续独立 change，参考项目 `godot_warcraft3/docs/roadmap/TODO.md:265` 自己也未做完；显式登记为后续 change 待办，见 `tasks.md` / `decision-memo.md`「## 已知限制 / 边界」）。
- JASS / wtg 触发器 VM（N5）、全科技树、地图编辑器 / RPG 自定义地图 / 剧情战役（N2–N4）、联机底座重做（P4 已交付）、AI × lockstep 新注入架构（Q6 / §0.3 T5）。
- 改活文档 `docs/references/WC3-MELEE-RULES.md`（附录 R6.5 降级 / R6.3 补锚 / 防误用补锚登记为 `docs-owner` 后续独立 change，Q5 / §14）、改 ADR、改主 `openspec/specs/**` 正文（归档才合并）。
- 本阶段不 apply / 不 commit / 不 archive / 不 self-approve / 不回填指纹 / 不改 `crates/` 任何文件；`w3-content` 原始 `f64` 坐标不进哈希 / 快照（ADR 0004）。
- 不据本 change 声称跨平台确定性有新验证或全平台达成（macOS / ARM64 / 其它 rustc 仍待验证，ADR 0002 复核记录 :100-108）。

## Decisions

> 每个决策统一列出：决策 / 备选方案（含否决理由）/ **ADR 0002 关联与对跨平台确定性的影响** / 架构原则对照 / 业务规则编号与核实状态（`[已核]` / `[待核]` / `[取舍]`）。跨平台确定性现状：仅 Windows 11 与 Debian 12 x86_64 / rustc 1.99.1 经离线 golden hash 逐字节比对验证（ADR 0002 复核记录 / 主 `cross-platform-determinism/spec.md`）；macOS / ARM64 / 其它 rustc 仍待验证，**本 change 不得声称有新验证或全平台达成**。**Q1–Q6 已于 2026-11-19 规格门经 `AskUserQuestion` 逐条拍板「全部按推荐」（见 `decision-memo.md`「## 拍板决策」P2 汇总与「## 待确认项」逐条拍板结果）：Q1 `SNAPSHOT_VERSION` bump 4 / Q2 新增独立 `ReviveHero` / `CancelRevive` 命令 + 事件变体 / Q3 复活常量放 `FrozenDefinitions` / Q4 酒馆买活 · 多英雄队列 · 技能点装备态一致性留后续 change / Q5 活文档修订登记为 `docs-owner` 后续独立 change 待办 / Q6 AI 席位复活决策留后续 AI · 联机 change；本 D 组按已拍板的单一口径成文，不再登记「待拍板」或「可容纳两种结果」**。

### D1：复活 = 祭坛队列项完成时「恢复同一个英雄实体」（承重决策）

- **决策**：祭坛复活 SHALL 作为训练 / 建造队列的一类队列项，携带目标英雄 `EntityId` + 待恢复状态快照；完成时 MUST **恢复同一个英雄实体**——同一 `EntityId`、`hero.level` / `hero.xp` / 技能等级 / 6 格背包逐项保留，置回存活、按冻结常量恢复生命 / 法力、改到祭坛位置。MUST NOT `entities.spawn()` 新实体、MUST NOT 得到 `hero=None` 空背包。英雄死亡 MUST NOT 删除实体、MUST NOT 判负（`apply_effects` 现状 :955-972 已保留死亡实体、`resolve_victory` :1368-1386 只看 `player.active`，为「恢复同一实体」提供可行前提）。
- **备选方案**：① 沿用 `complete_production` 的 `entities.spawn()` 生成新 `EntityId` + `hero=None`（`sim_match.rs:1314-1348`）→ **否决**：与 Warsmash `CUnit.java:2128-2160` / godot `apply_revived_hero_state`（`production_module.gd:216-233`）「恢复本体、背包保留」语义相反，不满足「复活后状态一致」验收线（C7 / R6.3）。② 表现层 HUD 假复活、`w3-core` 零改动（P1 被否 B）→ **否决**：C9 `EntityView` 不暴露英雄状态、C6 不扣费、C2–C4 权威状态无复活事实，需下调验收线，「降级验收 MUST NOT 静默采用」。③ 先做 P8.5e 迷雾、复活延后（P1 被否 C）→ **否决**：路线图 :121 串行顺序、P8.5a 在 P8.5e 之前。
- **ADR 0002 关联与跨平台确定性影响**：这是**新增 / 改写权威状态**的内核改动，不是零 diff 型 change。恢复本体复用既有死亡实体（`alive=false` → `true`），新增 `EntityId` 数为 0、稳定 `EntityId` 顺序不变；恢复的 level / xp / bag 均来自已进哈希 / 快照的 `UnitGameplayState`（`gameplay.rs:441-458`），不引入浮点 / 墙钟。命令排序键、30 Hz 整数帧、FNV-1a 编码方式不变。**跨平台确定性不因本 change 有新验证或新承诺**：恢复全走整数状态，与已验证的 Windows / Debian 12 x86_64 同机制；macOS / ARM64 / 其它 rustc 仍待验证。
- **架构原则**：唯一状态所有者（`RtsMatch` 仍是唯一写入者）、SRP（生产队列与复活队列同机制不同语义，见 D6）、显式失败不静默降级。
- **规则编号与核实状态**：R4.2 / R6.1 / R6.2 / R6.3 / R6.4 / R11.2 `[已核]`（机制），复活费用 / 时间 / 上限数值 `[待核]`、`[取舍]` 合成原创；Warsmash / godot 复活语义 `[已核]`（只读对照报告，仅锚机制）。

### D2：死亡登记 = 整数帧号 + `BTreeMap` 确定性有序容器 + 定义层类别驱动（承重决策）

- **决策**：英雄阵亡时 SHALL 登记一条死亡记录，键为稳定 `EntityId`、含整数逻辑帧号 `death_frame: u64` 与待恢复的英雄状态 / 背包 / 技能等级快照，落在 `BTreeMap` 确定性有序容器、按稳定 `EntityId` 顺序遍历。祭坛可用性 MUST 由定义层类别 `CATEGORY_ALTAR`（`defs.rs:42-54`）驱动，MUST NOT 用建筑 id 字符串白名单。MUST NOT 使用墙钟毫秒、渲染帧率、全局静态字典或 `HashMap` 迭代顺序。
- **备选方案**：① 照搬 godot `hero_death_registry.gd:33` 的 `died_at: Time.get_ticks_msec()` 墙钟毫秒 → **否决**：直接违反 ADR 0002 §2「`RtsMatch::step()` 不接受 delta / 墙钟 / 渲染帧率」（`docs/decisions/0002-determinism.md:30-34`），双端帧号不确定 → desync。② 照搬 godot `:9` 的 `static var` 全局字典 → **否决**：无确定性哈希 / 快照契约、跨对局残留、违反唯一状态所有者与 ADR 0002 §7「快照含全部状态」。③ 照搬 godot `:13-14` `can_revive_at` 硬编码建筑 id 字符串 `"halt"` → **否决**：违反 R1.2 / R13.3「由定义层数据驱动、不用建筑名白名单」，与 P8.0 D1 取舍冲突。④ 用 `HashMap` 承载死亡登记 → **否决**：ADR 0002 §3 禁止 `HashMap` 迭代顺序影响规则，须 `BTreeSet` / `BTreeMap`。
- **ADR 0002 关联与跨平台确定性影响**：死亡登记是新增权威状态，MUST 同步进 FNV-1a 状态哈希、由 `SNAPSHOT_VERSION` 定义的快照与 `first_difference()`（见 D5）；`death_frame: u64` + `BTreeMap` 保证两端逐帧逐字节一致、与平台无关，正是「把参考项目语义落到本项目确定性契约」的关键。墙钟 / 静态字典 / 白名单三个被否选项分别破坏帧确定性、状态所有权、定义层边界。不引入平台相关量。
- **架构原则**：确定性契约（最高硬红线）、唯一状态所有者、DIP（定义层类别驱动而非硬编码）、显式失败不静默降级。
- **规则编号与核实状态**：R1.2 / R4.2 / R13.3 `[已核]` + `[取舍]`（定义层类别驱动）、R6.3 / R11.2 `[已核]`、ADR 0002 §2-3 `[已核]`；`[待核]` 数值不得冻结进权威定义。
