# 架构设计原则 (Architecture Design Principles)

> 本文档是代码设计与架构决策的**原则层**：说明「为什么这样设计」以及「评审时如何判定」。
> **`CODEBUDDY.md` 是本项目单一权威开发约定**；本文只补充原则，不另立规则，冲突时以 `CODEBUDDY.md` 与 ADR 为准。
>
> 要点已注入三处，评审与生成 artifact 时会被用到：
> 1. `openspec/config.yaml` 的 `context` / `rules.design` —— `/opsx:propose` / `/opsx:apply` 生成 proposal 与 design 时作为约束；
> 2. `.codebuddy/agents/critic.md` —— 只读评审员的架构原则检查维度；
> 3. `CODEBUDDY.md` 第 1 节 —— 指向本文，保持单一权威。
>
> 来源：改写自另一项目的同名文档（Java / Spring 的 battle 服务端移植项目）。其项目级约束
> A1–A9 与 Spring / Nacos / 虚拟线程 / C++ 移植 / msgpack 线格式 / objguid 等专属内容已全部剔除；
> SOLID 等通用设计原则属公共知识，按 Rust 与本项目语境重写。

---

## 0. 适用边界（先读）

- 本项目：GPLv3、Rust edition 2024 虚拟 workspace，确定性模拟内核（ADR 0002）、冻结输入（ADR 0004）、Melee 优先（ADR 0003）。
- 术语映射：Java 的「类 / 接口 / 继承 / 依赖注入」→ Rust 的「模块 / trait / 组合 / 参数与泛型传参」；本项目**不引入容器或框架**。
- **确定性优先**：任何原则都不得与 ADR 0002 冲突（稳定顺序、零浮点、状态哈希与快照、整数帧）。
- 原则为指导方针而非教条；性能敏感、代码量极小、原型验证可适度放宽，但须在代码注释说明原因。硬红线见第 8 节。

---

## 1. 单一职责原则 (SRP)

**定义**：一个模块或类型应该有且只有一个引起它变化的原因。

**Rust 实践**
- crate 分层即职责边界：`w3-core`（权威模拟状态）、`w3-content`（冻结输入读取）、`w3-app`（注入边界）；内核不依赖上层。
- `RtsMatch` 是唯一状态所有者，但「状态所有权」不等于「上帝类型」：纯计算下沉到 `fixed` / `angle` / `nav` / `world` 等模块，`sim_match` 只做编排。
- 方法只做一件事，命名准确描述其唯一职责。

**违反信号**：模块名出现 `Manager` / `Handler` / `Processor` 且体积庞大；改一个功能要动同文件里不相关的代码；结构体字段分属不同业务域。

---

## 2. 开闭原则 (OCP)

**定义**：对扩展开放，对修改关闭。

**Rust 实践**
- 用 `enum` + `match` 显式枚举命令种类（`CommandKind`），新增命令走新变体并在一处补齐 `match`，避免散落的 `if-else` 分支。
- 用 trait / 泛型 / 组合预留扩展点，而不是硬编码分支；冻结输入由 app 层注入 `StaticWorld`，内核不读文件（ADR 0004）。
- **例外（硬门禁）**：新增权威状态字段 MUST **同时**进入 `compute_state_hash()`、`capture_snapshot()` / `restore_snapshot()` 与 `first_difference()`（ADR 0002），这不是可跳过的扩展点。

**违反信号**：每次新增功能都在原有函数里加分支；新增功能导致既有测试失败；改一处导致多处不相关代码联动。

---

## 3. 里氏替换原则 (LSP)

**定义**：trait 实现必须满足 trait 契约，调用方无需知道具体类型。

**Rust 实践**
- 实现不得加强前置条件或削弱后置条件；不得用 `unimplemented!()` / `todo!()` / 空实现占位。
- 使用 trait object / 泛型时，调用方不应 downcast 到具体类型才能正确工作。
- 错误路径显式（`Result` / `FixedError` / `SnapshotError` / `CommandError`），不静默降级、不吞错。

**违反信号**：调用方需 `match` 具体类型；实现为空或直接 `panic!`；同一 trait 的不同实现行为不一致。

---

## 4. 依赖倒置原则 (DIP)

**定义**：依赖抽象，不依赖具体实现。

**Rust 实践**
- `w3-core` **零依赖**，不依赖 `w3-content` / `w3-app` / `render` / `ui` / `audio` / `net`（ADR 0002）；依赖方向只能是 app → core。
- 跨层交互用中立数据类型（`SimFixed` / `StaticWorld` / `Command`），不暴露内部可变集合；`read_view()` 返回所有权拷贝。
- 依赖通过参数 / 构造传入，不在内部直接实例化；平台差异在脚本内用 `os.name` / `process.platform` 判断（CODEBUDDY.md 第 2 节）。

**违反信号**：内核直接调用内容层或做文件 IO；上层直接读写内核私有字段；替换底层组件要改大量上层代码。

---

## 5. 接口隔离原则 (ISP)

**定义**：不强迫调用方依赖它们用不到的方法。

**Rust 实践**
- trait 按角色拆分、保持精简；一个类型可实现多个小 trait，而非一个臃肿的大 trait。
- 公共 API 面尽量小（`lib.rs` 只重导出必要类型）。

**违反信号**：实现里有大量空方法；trait 方法过多（通常超过 5–7 个应考虑拆分）；不同调用方只用互不重叠的少数方法。

---

## 6. 迪米特法则 (LoD)

**定义**：最少知道原则，一个对象应对其他对象有尽可能少的了解。

**Rust 实践**
- 避免长链式访问穿透多层；通过封装方法隐藏内部结构。
- 不暴露可变内部集合：`RtsMatch` 字段全私有，公开读取一律返回 owned 拷贝。

**违反信号**：多层链式调用；一个模块需了解依赖对象的内部结构才能工作；改内部结构导致大量不直接依赖它的模块改动。

---

## 7. 组合 / 聚合复用原则 (CARP)

**定义**：优先使用组合，少用继承来复用。

**Rust 实践**
- Rust 无实现继承；用结构体组合 + trait 实现复用（如 `UnitState` 组合 `Angle` / `SimFixed` / `Order`）。
- 不要为了复用少量方法而强造 trait 层次；深层继承在 Rust 里本就不存在。

**违反信号**：trait 层次过深（通常超过 3 层应审视）；为复用而引入并无真实类型关系的抽象。

---

## 8. 本项目硬红线（评审判定依据）

以下是本项目既有契约的具体落地形态，**不是通用原则**，评审时优先级最高；「历史代码就这样」不构成豁免。

| 编号 | 约束 | 依据 |
|---|---|---|
| B1 | 确定性：权威状态只用 `SimFixed` 整数数学；整数帧、30 Hz 冻结；命令按 `ExecuteFrame → PlayerId → Sequence → Arrival` 稳定排序；稳定 `EntityId` 顺序；FNV-1a 状态哈希；新增权威字段必须同时进哈希 / 快照 / `first_difference()` | ADR 0002 |
| B2 | 状态所有权：`RtsMatch` 是唯一写入者；`read_view()` 返回 owned 拷贝；表现层不得反写模拟状态 | ADR 0002 |
| B3 | 分层与冻结输入：`w3-core` 不反向依赖上层；`w3-content` 的原始 `f64` 是冻结输入，不进权威状态 / 快照 / 哈希；转换规则由 ADR 0004 冻结 | ADR 0002 / 0004 |
| B4 | 显式失败：溢出 / 除零 / 版本 / `sim_version` / 内容哈希 / 世界身份不匹配 MUST 显式报错，**禁止静默降级或本地兜底** | ADR 0002 / 0004 |
| B5 | 只读参考：四个上游项目只读、不复制代码；`WarsmashModEngine` 为 AGPLv3，引入前须按 ADR 0001 复核；仓库不含任何游戏资产或派生文件 | ADR 0001 |
| B6 | 工具链：Rust 源码遵循 rustfmt 默认风格（写完 `cargo fmt --all`、提交前 `--check`）；工具脚本跨平台 Python / Node；提交信息描述中文 | CODEBUDDY.md §2 / §3 |

## 9. 原则应用优先级

1. **正确性 / 确定性**（ADR 0002 硬门禁）> 所有原则
2. **可读性** > 过度抽象（不要为了原则而原则）
3. **本项目硬红线 B1–B6** ≈ **SRP** ≈ **OCP** > **DIP** > **ISP** > **LSP** > **LoD** > **CARP**

> **B1–B5 为绝对红线，任何场景不得放宽**；B6 为流程约定，同样不得跳过。其余原则在性能敏感、代码量极小或原型验证场景下可适度放宽，但须在代码注释中说明原因。

## 10. 代码评审检查清单

在 Code Review 时对照以下条目快速检查（与 `critic.md` 的架构原则维度一致）：

| # | 检查项 | 对应 |
|---|--------|------|
| 1 | 这个模块 / 类型是否只做一件事？ | SRP |
| 2 | 新增功能是通过扩展还是修改已有分支实现的？ | OCP |
| 3 | trait 实现是否满足契约、调用方是否需要 downcast？ | LSP |
| 4 | 依赖的是抽象还是具体实现？`w3-core` 是否反向依赖上层？ | DIP |
| 5 | trait / 公共 API 是否足够精简？ | ISP |
| 6 | 是否存在跨层链式访问、是否暴露可变内部集合？ | LoD |
| 7 | 复用是否用组合，而非强造 trait 层次？ | CARP |
| 8 | 新增权威字段是否同时进入哈希 / 快照 / `first_difference()`？ | B1 |
| 9 | 是否有 `f64` / `HashMap` 迭代 / 墙钟 / 异步完成顺序进入权威状态？ | B1 |
| 10 | 冻结输入是否留在注入边界、未进入权威状态？ | B3 |
| 11 | 错误路径是否显式（`Result` / `Error`），有无静默兜底？ | B4 |
| 12 | 是否复制了只读参考项目的代码或资产？ | B5 |
| 13 | `cargo fmt --all -- --check` 是否通过、提交信息描述是否中文？ | B6 |
